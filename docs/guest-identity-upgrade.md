# 游客身份安全升级（已在隔离环境验证，未部署）

## 部署顺序与影响

1. 备份数据库，在**非生产副本**依次验证 `backend/migrations/001_guest_identity.sql` 与 `backend/migrations/002_notification_drafts.sql`，再由维护人员安排生产迁移。已在独立合成旧结构 MariaDB 11.8.6 数据库运行验证，未接触生产数据库；目标 MySQL 版本仍需验证。
2. 数据库增加 `users.is_guest` 与 `notification_drafts` 表后才可运行本版本后端。生产 `synchronize` 已强制关闭；非生产也仅在显式设置 `DB_SYNCHRONIZE=true` 时开启。不要靠 ORM 自动同步生产结构。
3. 新后端把 `identityVersion` 从 1 升到 2。**全部旧 JWT 会立即失效**，包括普通用户、主办方、超管和游客。注册用户用密码重新登录；参与者无需注册，可继续匿名使用。
4. 新游客的 `/auth/guest` 响应含 `guest_id` 与一次性生成的 256 位 `guest_secret`。客户端保存两者供后续恢复；服务端只存 bcrypt 哈希。`device_id` 保留兼容字段，但不再是身份凭据。遗失持有凭证后不能靠设备 ID 恢复。

## 历史游客数据

旧版用可预测的 `guest_<device_id>` 标识和服务端未知随机密码建号，也允许直接用 `device_id` 命中任意用户。这种标识不能证明归属。迁移只给旧账号 `is_guest=0`，**不得按用户名批量标记或让旧设备 ID 找回账号**。旧客户端在没有新凭证时会获得一个新游客身份，已有投稿/报名等记录不会自动迁移。需要旧数据时，应由平台人工核实多项独立证据后处理，不能仅凭设备 ID、用户名或旧 JWT。

注册与游客数据合并尚未开放。注册只创建普通用户，只有超管用户管理接口能赋予主办角色。后续如实现合并，应要求当前游客持有凭证及目标注册账号密码，并在事务中检查各记录归属与冲突。

## 客户端兼容

旧客户端仍可发送 `{ "device_id": "..." }`，会创建**新**游客，且每次无凭证请求都会创建新身份。新客户端保存并回传 `{ "guest_id": 123, "guest_secret": "..." }`。若只传其中一项或凭证错误，接口返回 401，不回退到按设备 ID 查找。

新客户端明确登出时会删除本机游客凭证，之后无法自动恢复该游客的旧记录。清除浏览器存储也有相同结果。普通用户登录不会把此前游客数据自动合并到注册账号。

本补丁未轮换生产 JWT 密钥，也未执行部署。上线前需准备用户重新登录公告与历史游客记录的人工支持方案。

## Linux 独立验证

- 后端 `npm test`：覆盖新游客、凭证恢复、猜测标识、畸形凭证、旧 JWT、数据库实时角色、禁用账号、密码入口隔离、日志脱敏及超管授权边界。
- 前端 `npm test`：覆盖首次并发初始化共用请求、凭证持久化/恢复、显式退出及迟到的游客或资料响应；不会在退出后恢复游客，也不会覆盖已完成的注册用户登录。
- 前端 `npx tsc --noEmit -p tsconfig.json` 与 `npm run build`：独立执行类型检查和生产打包。
- 2026-10-01 在原 NestJS 后端和独立 MariaDB 11.8.6 上完成真实 HTTP/数据库及旧结构迁移验证，包括旧 JWT 拒绝、游客恢复、角色/归属边界、历史记录保留和生产同步保护。后端测试 21/21、前端测试 23/23（含 6 个真实 React/Ant Design 路演组件用例）、类型检查与生产构建均通过。
